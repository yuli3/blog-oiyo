## 프롬프트는 한 번에 완성되지 않는다

실무에서 좋은 프롬프트는 대개 한 번에 나오지 않습니다. 초안을 만들고, 결과를 확인하고, 빠진 조건을 보완하고, 다시 실행하면서 다듬습니다. 그래서 프롬프트 엔지니어링은 문장 기술이면서 동시에 작은 실험 절차입니다.

모델과 기능은 변할 수 있으므로 특정 결과가 영원히 같은 방식으로 나온다고 기대하면 안 됩니다. 중요한 업무일수록 프롬프트, 입력 자료, 출력 예시, 검토 기준을 함께 기록해야 합니다.

## 기본 워크플로

프롬프트 업무화는 목적 정의에서 시작합니다. 무엇을 자동화하려는지, 사람이 어디서 검토할지, 실패하면 어떤 위험이 있는지를 먼저 정해야 합니다.

| 단계 | 할 일 | 산출물 |
|---|---|---|
| 1. 목적 정의 | 줄이고 싶은 반복 작업 확인 | 작업 설명 |
| 2. 입력 정리 | 필요한 자료와 조건 모으기 | 입력 템플릿 |
| 3. 프롬프트 작성 | 역할, 지시, 형식 지정 | 프롬프트 초안 |
| 4. 결과 평가 | 정확성, 누락, 톤 확인 | 수정 목록 |
| 5. 반복 개선 | 예시와 제약 보완 | 안정화된 버전 |

## 평가 기준 만들기

좋은 결과인지 판단할 기준이 없으면 프롬프트를 개선하기 어렵습니다. 평가 기준은 정답 여부, 형식 준수, 누락 여부, 독자 적합성, 사실 확인 필요 여부처럼 구체적이어야 합니다.

```text
아래 답변을 평가해 줘.

평가 기준:
- 요청한 형식을 지켰는가
- 핵심 정보가 빠지지 않았는가
- 과장되거나 단정적인 표현이 있는가
- 초보자가 이해하기 쉬운가

각 항목을 상/중/하로 평가하고 개선 문장을 제안해 줘.
```

## 프롬프트 버전 관리

반복해서 쓰는 프롬프트는 파일이나 문서로 관리하는 편이 좋습니다. 목적, 입력 예시, 출력 예시, 마지막 수정일, 실패 사례를 함께 남기면 팀원이 이어서 개선하기 쉽습니다.

| 기록 항목 | 이유 |
|---|---|
| 목적 | 프롬프트가 해결하는 문제를 명확히 함 |
| 입력 예시 | 어떤 자료를 넣어야 하는지 보여 줌 |
| 출력 예시 | 기대 결과를 공유함 |
| 실패 사례 | 반복 오류를 줄임 |
| 검토자 | 최종 판단 책임을 분명히 함 |

## 실전 적용 순서

처음부터 큰 업무 전체를 자동화하려고 하지 말고 작은 단위부터 시작합니다. 회의록 요약, 이메일 초안, 표 정리처럼 실패해도 사람이 쉽게 고칠 수 있는 작업이 좋습니다. 안정되면 검토 체크리스트와 예시를 추가해 범위를 넓힙니다.

## 핵심 요약

- 프롬프트는 초안, 평가, 수정, 재실행을 거치며 개선된다.
- 업무에 붙일 때는 목적, 입력, 출력, 검토 지점을 먼저 정해야 한다.
- 평가 기준이 있어야 결과 품질을 비교하고 개선할 수 있다.
- 반복 사용 프롬프트는 버전과 실패 사례를 기록하는 것이 좋다.

이 시리즈를 마쳤다면 자주 하는 업무 하나를 골라 입력 템플릿, 프롬프트, 평가 기준을 한 문서로 정리해 보세요.
