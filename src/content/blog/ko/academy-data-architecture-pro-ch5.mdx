## 물리 설계는 모델의 실행 조건입니다

데이터베이스 설계는 논리 모델을 실제 운영 환경에 맞게 구현하는 단계입니다. DAP에서 중요한 것은 특정 DBMS 기능 이름을 외우는 것보다, 모델 구조가 성능과 운영성에 어떤 영향을 주는지 설명하는 능력입니다. 테이블, 인덱스, 파티션, 제약 조건, 저장 구조는 모두 업무 사용 패턴과 연결되어야 합니다.

### 성능 설계의 관점

| 관점 | 확인 내용 |
|---|---|
| 접근 경로 | 주요 조회 조건과 조인 경로 |
| 인덱스 | 선택도, 갱신 비용, 중복 여부 |
| 파티션 | 대용량 데이터의 분할 기준 |
| 제약 조건 | 무결성 유지와 입력 통제 |

성능 문제는 SQL 튜닝만으로 해결되지 않습니다. 처음부터 관계가 불필요하게 복잡하거나, 기준 정보가 중복되어 있거나, 대량 이력 테이블의 파티션 기준이 업무 조회와 맞지 않으면 운영 단계에서 비용이 커집니다. 그래서 물리 설계는 논리 모델의 의미를 훼손하지 않는 범위에서 성능과 관리성을 조정하는 일입니다.

## 시험에서 보는 포인트

문제 문장에서 “대량 조회”, “이력 데이터”, “빈번한 갱신”, “조인 성능 저하” 같은 단서가 나오면 물리 설계 관점으로 읽으세요. 다만 모든 성능 요구가 반정규화나 인덱스 추가로 끝나는 것은 아닙니다. 데이터 정합성과 운영 비용을 함께 비교해야 합니다.

## 핵심 요약

- 데이터베이스 설계는 논리 모델을 운영 환경에 맞게 구현하는 과정입니다.
- 성능은 접근 경로, 인덱스, 파티션, 제약 조건과 함께 판단합니다.
- DAP에서는 빠른 구조와 정확한 구조의 균형을 설명할 수 있어야 합니다.
