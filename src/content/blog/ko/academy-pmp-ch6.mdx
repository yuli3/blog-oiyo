## 애자일 선언 (2001)

4가지 가치:
1. **프로세스와 도구**보다 **개인과 상호작용**
2. **포괄적인 문서화**보다 **작동하는 소프트웨어**
3. **계약 협상**보다 **고객과의 협력**
4. **계획 준수**보다 **변화에 대응**

## 스크럼 프레임워크

### 3가지 역할

**프로덕트 오너(PO)**:
- 프로덕트 백로그 소유·우선순위 결정
- 비즈니스 가치 극대화
- 이해관계자와 팀 사이의 가교

**스크럼 마스터(SM)**:
- 스크럼 프로세스 촉진
- 장애물(impediment) 제거
- 서번트 리더십 (팀 보호, 지원)

**개발 팀(Development Team)**:
- 자기조직화, 교차기능 팀
- 3~9명
- 스프린트 내 "완료"된 증분 전달

### 5가지 이벤트

| 이벤트 | 시간박스 | 목적 |
|-------|---------|------|
| **스프린트** | 1~4주 | 실행 단위 |
| **스프린트 계획** | 최대 8시간 | 스프린트 목표·백로그 선택 |
| **일일 스크럼** | 15분 | 동기화, 장애물 파악 |
| **스프린트 리뷰** | 최대 4시간 | 증분 시연, 피드백 |
| **스프린트 회고** | 최대 3시간 | 프로세스 개선 |

### 3가지 산출물

**프로덕트 백로그**: PO가 관리하는 요구사항 목록 (우선순위 순)

**스프린트 백로그**: 현재 스프린트에서 완료할 항목 목록

**증분(Increment)**: 각 스프린트 종료 시 출시 가능한 완성품

<Callout type="tip">
**완료의 정의(DoD)**: 작업 항목이 "완료"됐다고 말할 수 있는 기준. 팀 전체가 동의한 명확한 DoD가 없으면 품질 문제가 발생합니다. 스크럼의 핵심 개념입니다.
</Callout>

## 칸반 (Kanban)

작업 시각화와 WIP(진행 중 작업) 제한을 통해 흐름을 최적화하는 방법.

```
할 일 | 진행 중(최대 3) | 검토 중(최대 2) | 완료
───────────────────────────────────────
task1  |   task3         |    task5       |task6
task2  |   task4         |               |
```

**WIP 제한**: 동시에 진행할 수 있는 작업 수 제한 → 멀티태스킹 감소 → 처리량 향상

---

## 속도(Velocity)와 번다운 차트

**속도(Velocity)**: 팀이 스프린트당 완료하는 평균 스토리 포인트. 미래 용량 예측에 사용.

**번다운 차트(Burndown Chart)**: 남은 작업량이 시간에 따라 줄어드는 추세.

```
스토리 포인트
↑
|  ╲ 이상적 선
|    ╲___
|         ╲ 실제 선
|              ╲
+──────────────── 스프린트 일수
```

## 핵심 개념 카드

**PO vs SM vs Dev Team** ★★★★★
: PO=무엇을(백로그 우선순위), SM=어떻게(프로세스 촉진), Dev Team=실행(자기조직화).

**완료의 정의(DoD)** ★★★★★
: 팀이 합의한 "완료" 기준. 없으면 기술 부채 누적과 품질 문제 발생.

**WIP 제한** ★★★★☆
: 칸반의 핵심. 동시 작업 제한으로 흐름 개선, 병목 가시화.

## 실전 퀴즈

**Q1. 스프린트 도중 스테이크홀더가 긴급 기능 추가를 요청했다. 스크럼 마스터는 어떻게 해야 하는가?**
> 현재 스프린트 목표를 보호합니다. 긴급 요청은 프로덕트 오너가 프로덕트 백로그에 추가하고 다음 스프린트 계획에서 우선순위를 결정합니다. 스프린트 도중 중단은 팀의 흐름을 방해하므로 원칙적으로 허용하지 않습니다.

**Q2. 스크럼에서 자기조직화 팀의 의미는?**
> 팀이 스프린트 목표를 달성하는 방법을 스스로 결정한다는 것입니다. PM이나 외부에서 세부 작업 방식을 지시하지 않고, 팀이 자율적으로 작업 분배와 방법론을 결정합니다. 이것이 애자일에서 창의성과 혁신이 나오는 원천입니다.
